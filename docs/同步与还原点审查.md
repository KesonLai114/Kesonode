# Kesonode 同步与备份（还原点）机制审查

基线：v1.5.12 工作区。文中定位以**函数名**为准（行号会随改动漂移）。

---

## 0. 结论摘要

1. **整体骨架是健壮的，不需要重构。** 单一 `sync()` 入口 + 两道锁、按数据类型隔离失败、合并全程加性（LWW + 墓碑 + 双向闸）、破坏性操作前写还原点、限流断路器、未变更文件不发请求。上一轮"限流风暴"的两个根因（403 被就地吞掉、请求放大）确实是从结构上修掉的，不是打补丁。
2. **本次发现并修复 3 个"会周期性复发"的缺陷**，都属于"故障发生了但没人知道 / 知道了也没退避"这一类：
   - **P0** Drive、GitHub 的限流根本没进入断路器。冷却只认 `HttpError.rateLimited`，而只有 WebDAV 会置这个位；这两家的限流是 **403**（原因藏在 body / 响应头里），于是被当成普通硬错误，**每分钟重试一次、永不退避**——和坚果云那次是同一个病，换了件衣服。
   - **P0** 首次同步选"用远端副本"时，前置还原点写不出来只记一条 warning 就继续替换本地书签。这是全产品唯一一个**一次点击能毁掉本地数据**的操作，必须有备份前置条件。
   - **P0** peer 文件"存在但读不了"（超过 25 MB 上限 / JSON 损坏）被静默跳过，且**不会自愈**（对方 `uploadIfChanged` 认为内容没变，永不重写）。结果是某台设备的数据永久不合并，UI 却报"已同步"。
3. **5 项 P1 建议已全部落地**（见第 3 节）：硬失败退避、还原点环形缓冲语义、设置备份凭据说明、共享索引条件写、事故还原点复用连接。只剩"上传侧体积上限"一项保留。
4. 一个长期结构性限制本轮处理掉了：**跨设备写入现在有条件写**（`IBackend.getFileVersion` / `putFileIfVersion`，WebDAV `If-Match`、Drive `etag`、GitHub blob sha）。之前共享的 `konode_snap_index.json` 偶发丢注解（命名、计数、来源），不丢还原点数据本身；现在并发写会失败重读再合并。

## 1. 当前链路梳理

### 1.1 触发源

| 触发 | 代码位置 | 特点 |
| --- | --- | --- |
| 周期 alarm | `utils/alarms.ts: ensureSyncAlarm` | 只创建不重建，避免每次 worker 唤醒把下一次触发推后 |
| 书签变更 | `service-worker: onBookmarkChange` | 1 s 防抖快路径 + 0.5 min 一次性 alarm 兜底（worker 被回收也不丢） |
| 手动 | `SYNC_NOW`（`force: true`） | 不受冷却限制，是用户的重试入口 |
| 操作型消息 | RESTORE / APPROVE_BULK_DELETE / FIRST_SYNC_CHOICE | 均 `await` 同步，用 pending 响应把 MV3 worker 撑住 |

### 1.2 入口保护顺序（这个顺序是有讲究的，改动需谨慎）

`isSyncing` 同步抢占 → 冷却检查（仅非 force）→ 后端配置存在 → 数据类型非空 → 持久锁 `acquireSyncLock`(TTL 2 min) → 置 `syncing`。

- 锁的所有权在取锁与 `try` 之间**不允许有 await**（否则 `finally` 拿不回锁）。
- 收尾 `finishSync`：先同步清 `isSyncing`，再分别 try/catch 释放锁与 `disconnect()`——任一步抛错都不会把锁留到 TTL。
- 新 worker 启动时 `clearStaleSyncLock()` 无条件清锁：MV3 单 worker，新上下文里不存在"还有人持有"。

### 1.3 单类型流程（`syncType`）

拉取全部 peer（按包时间戳**新→旧**排序，旧→新会让墓碑失效、复活已删书签）→ `pruneVanishedPeers`（按文件清单判存在，不按包判）→ 构建本地 payload → 本地变更守护（在合并**前**度量漂移）→ 分流：

- 无 peer：有内容才上传；
- `manual` 且书签/历史：按 peer 逐条排冲突卡（内容哈希去重，已解决过的同内容不再排），**仍然上传自己的文件**（manual 只关导入，不关导出）；
- 其它：新→旧逐 peer 折叠，单个 peer 失败只跳过它；合并后**重读**本地 payload（书签/历史被改写）再决定上传。

上传统一走 `uploadIfChanged`：`sha256(payload)` + 信封版本 + 目标位置 + 设备名 + 加密形态 组成 tag，与上次一致则跳过；`ownFilesMissing`（文件被别的设备"忘记"或手工删掉）会强制重传。

### 1.4 收尾与可见性

问题面聚合三处：类型级错误、加密不一致（按 peer 去重）、`backend.failedPeers`（读不到的 peer）。状态优先级 `error > conflict > success`；连续同类告警用"每事件一次"的闩锁（`permissionWarned` / `getListFailureNoted` / `getRecoverySnapshotTaken`）压住日志放大。

### 1.5 备份（还原点）机制

- 文件：`konode_snap_bookmarks_<epochms>.json`（自动点，滚动保留最新 10 个，`pruneSnapshots` 以**后端文件清单**为准而非本地索引）、`konode_snap_manual_<epochms>.json`（手动点，独立 10 个槽位）、`konode_snap_kept_<epochms>.json`（永久，剪枝只走两个滚动前缀，任何设备/旧版本都动不了它）。
- 注解：共享索引 `konode_snap_index.json`（加密设置开启时整份加密）；读不到时**绝不覆盖**，本地保留一份"最后成功读到的共享索引"仅用于显示；写入在支持的后端上走条件写（ETag/sha），冲突则重读重试。
- 还原 `restoreSnapshot` → `restoreBookmarks`：**加性**恢复（只补本地缺失的 URL，按兄弟位置插入），并清掉这些 URL 的墓碑；开启 E2EE 时拒绝恢复未加密的还原点（防降级注入）。
- 自动还原点：大额删除被闸门拦下、本地变更守护扣住上传，各写一次（按事件闩锁，避免槽位在十分钟内被同一个事故刷掉），且复用同步已建立的连接。

## 2. 本次修复（P0，已落地）

### 2.1 Drive / GitHub 限流现在也会 park 同步

- `GDriveBackend`：新增 `rateLimited` 与 `httpError()`，按 `error.errors[0].reason` 识别 `rateLimitExceeded` / `userRateLimitExceeded` / `quotaExceeded` / `dailyLimitExceeded`；429 兜底。`storageQuotaExceeded` 单独文案（空间满≠等一等就好）。
- `GitHubBackend`：新增 `rateLimited` 与 `httpError()`，403/429 且 `x-ratelimit-remaining: 0` 或带 `retry-after`（次级限流）判为限流；token 权限不足的普通 403 不受影响。
- 两个后端所有失败响应都改走 `httpError()`，包括 peer 文件 GET（这样 `withPeerRetry` 的"限流不重试"分支才真正生效）。
- 引擎侧不用改：`noteRateLimit()` 已经认 `err.rateLimited`，30 分钟冷却沿用既有实现。

### 2.2 "用远端副本"必须先拿到还原点

`chooseFirstSync`：`remote` 分支的 `snapshotNow()` 失败改为**抛错中止**（什么都没动，问题留在屏幕上，可重选）；`local` 分支保持 warning——它只删 peer 文件，对方设备会重新上传。

### 2.3 读不到的 peer 文件计入 `failedPeers`

WebDAV（超 25 MB ×2 处、JSON 损坏）、Drive、GitHub 的跳过分支都登记到 `failedPeers`，并带上体积/原因；引擎侧文案改为"Activity 里逐个文件说明原因"。

## 3. 建议继续做（P1）— 本轮已全部落地

1. **硬失败退避（已做）。** `noteSyncFailure` 以**错误文案本身**作为"同一次失败"的判据，不做"这是不是永久错误"的猜测（猜错的两个方向都糟：藏掉真问题，或让风暴继续）。第 1 次失败不暂停（掉线、503 都只发生一次）；同一句文案连续出现时 2 → 4 → 8 → 15 分钟（上限），`sync()` 门禁返回 `backing-off`。清零路径：本轮成功、`force`（Sync now）、保存设置。日志只在"文案首次出现"与"暂停仍在增长（streak ≤ 5）"时落盘，重复走 console。限流不进这套计数，仍走 30 分钟冷却（否则短暂停会在长窗口到期后继续存在）。
2. **还原点环形缓冲的语义（已做）。** 手动点写入 `konode_snap_manual_<ts>.json`，单独 10 个槽位；自动点留在 `konode_snap_bookmarks_*`；`konode_snap_kept_*` 依旧不受剪枝。判据放在**文件名**里而不是共享索引里——索引可能读不到（限流/口令不匹配），而"这个点是谁要的"必须在那种时刻依然成立，且旧版本设备看不到前缀就不会误删。
3. **设置备份的凭据明文（已做）。** 导出确认框原本是硬编码中文，现走 `_locales`（11 语言）；`PRIVACY.md` 增「Settings backup」一节，写明这份文件含 WebDAV 密码 / GitHub 令牌 / Google 刷新令牌 / 加密口令、只有一个校验和、且**无法**加密（文件本身就是口令的载体）。导入侧的风险确认保持不变。
4. **共享索引条件写（已做）。** `IBackend` 增 `getFileVersion` / `putFileIfVersion`：WebDAV `If-Match`（或创建时 `If-None-Match: *`）+ ETag，GitHub 复用已有的 blob sha（409/422 视为"别人先写了"），Drive 用 `files.get` 的 `etag` + `If-Match`。`updateIndex()` 统一了 merge/rename/move 三处 read-merge-write：最多 3 次条件重试，最后 1 次无条件写入——改进不能反过来把写入弄丢。拿不到 ETag/SHA 的后端自动退回原来的行为。
5. **事故还原点复用连接（已做）。** `snapshotNow(opts, open?)` 接受已连接的 backend，`recordBlockedDeletion` / `recordGuardIncident` 从 `sync()` 里把手上的连接传进去，省掉一次 connect（MKCOL/PROPFIND）。顺带：`recordGuardIncident` 之前没传 `origin`，Activity 会把"变更守护"的自动点显示成用户自己点的，现在标 `auto`。
6. **（未做，保留）上传侧没有体积上限。** GitHub Contents API 对大文件有硬上限，超大 history 包会永久失败且解释不清。建议在 `uploadIfChanged` 按后端给阈值 + 明确文案（与下载侧 25 MB 对称）。这一项需要先量一下真实 history 包的大小分布，本轮没动。

## 4. 已确认是"有意设计"，不建议改

- **合并从不删除**（删除靠墓碑 + LWW + 双向闸）：这是数据安全的核心假设，改成"以某端为准"会立刻把偶发同步事故升级成数据丢失。
- **冷却不拦"Sync now"**：手动同步是用户绕过故障的唯一手段，也是冷却的解除途径。
- **首次同步探测失败回落普通合并**：一次 listing 失败不该让新设备停止同步。
- **`manual` 仍然上传**：不这样做，manual 设备上的改动永远到不了别的设备，而它自己会显示"同步成功"。
