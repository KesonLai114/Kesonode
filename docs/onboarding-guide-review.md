# Kesonode 安装后引导：现状梳理与优化方案

基线：v1.5.12（当前工作区）。文中 `file:line` 均指当前代码。

---

## 0. 结论摘要

1. **链路骨架已经成型，但缺一个状态：已配置。** 引导页只判断 `?reason=permissions`，没有判断 `onboarding_completed`。已配置用户重新打开 `onboarding.html`（刷新已完成的标签页、书签、手动访问 URL）并走完流程，会用自己的默认选择覆盖 `backends`、`enabled_types`、`active_backend`。这是本次评审中唯一会**实质性破坏用户配置**的缺陷，属于 P0。
2. **权限是当前最大的信任缺口，问题不在"有没有申请"，而在"什么时候申请、怎么解释、用什么语言解释"。** 安装期就要求 4 个主机权限（Google / GitHub，WebDAV 用户完全用不到）；可选权限全部压到"完成并同步"那一次点击里一次性弹出；更新后的权限页把 `history`、`tabs`、`management`、`https://host/*` 这些标识符直接打在屏幕上。
3. **流程上有 5 处会直接造成误解或操作浪费**：首帧总是先渲染 `welcome`（更新模式下会闪一下 welcome 页）、设备名在两个步骤各问一次、数据步骤允许 0 类型通过、同步步骤 20 秒即判定超时且不显示任何数量、完成页与产品核心循环（第二台设备）完全脱节。
4. **界面层三个高频问题**：存储步骤 8 张卡片纵向平铺、认证面板内联展开，首屏看不到"继续"；引导页没有任何 `@media` 规则，360px 手机上正文宽度只剩约 256px；emoji 图标（🔒⚡🌐📦🎉）与设置页的 lucide 图标体系不一致。
5. **更新场景目前几乎是静默的。** 只有"缺权限"才开页面，其余情况用户不知道版本变了、不知道改了什么。建议做成"有动作才打扰，无动作只在弹窗留一次性入口"。

建议按 **P0（5 项，改动量 S–M）→ P1（10 项）→ P2（打磨）** 三批落地。P0 全部可在不改数据模型的前提下完成。

## 1. 现状梳理

### 1.1 四个入口

| 入口 | 触发条件 | 落地 | 已知失效场景 |
|---|---|---|---|
| 首次安装 | `onInstalled` reason=install | `onboarding.html` 新标签页 | WebKit/Orion 上 `tabs.create` 静默失败（代码里已承认） |
| 版本更新 | reason=update **且** `missingPermissionsFor()` 非空 | `onboarding.html?reason=permissions` | 权限齐全时完全静默，无任何变化提示 |
| 弹窗兜底 | `!onboarding_completed && !hasBackend` | 卡片 CTA → 引导页 | 仅在"未完成且无后端"时出现，完成后无入口 |
| 设置页兜底 | `!onboarding_completed && !setupComplete` | 两步清单卡片，跳转到对应 Tab | 卡片只有 2 步（存储/类型），与实际 4 步向导不一致 |
| 重装恢复 | 欢迎页"已有配置备份？" | 导入 → 权限检查 → `imported` 页 | 依赖用户先导出过；未导出者无路可走 |

关键证据：`src/background/service-worker.ts:507-528`、`src/popup/App.tsx:370`、`src/options/App.tsx:1512`。

### 1.2 向导步骤

```
welcome ──▶ backend ──▶ data ──▶ encrypt ──▶ syncing ──▶ done
   │                        │                     │
   │                        │                     ├─▶ direction（云端有他人书签时插入）
   └── import ──▶ permissions? ──▶ imported
```

- 进度指示：`STEPS = [welcome, backend, data, encrypt, done]`，去掉 `done` 后画 4 个圆点，`position: fixed` 固定在顶部（`App.tsx:771-780, 1448-1451`）。
- `syncing` / `direction` / `permissions` / `imported` 都是非步骤态，但共用同一张卡片容器。
- 步骤内容分布：
  - welcome：品牌、4 条 emoji 卖点、**设备名输入**、备份导入面板、"开始使用"（`783-830`）
  - backend：8 张服务商卡片 + 内联认证面板 + 底部导航（`833-1011`）
  - data：4 个类型开关 + 书签排除树 + **设备名输入（第二次）** + 继续（`1014-1128`）
  - encrypt：E2EE 开关（默认关）+ 口令/确认/生成密钥 + "完成并同步"（`1130-1232`）
  - done：🎉 + 3 条固定勾选 + 关闭/打开设置（`1344-1368`）

### 1.3 权限时序

| 权限 | 类型 | 申请时机 | 用户看到 |
|---|---|---|---|
| `bookmarks` | 必需 | 安装时 | 商店/浏览器安装警告，无站内解释 |
| `storage` `alarms` `notifications` `unlimitedStorage` | 必需 | 安装时 | 无警告 |
| `identity` | 必需 | 安装时 | 即使只用 WebDAV 也必须持有 |
| `https://www.googleapis.com/*` 等 4 项 | 必需 host | 安装时 | 即使只用 WebDAV 也要授权 |
| `history` `tabs` `management` `tabGroups` | 可选 | 向导"完成并同步"时**合并一次**请求 | 点击后才弹窗，此前无预告 |
| `https://<自建主机>/*` | 可选 host | 同上 | 同上 |

证据：`public/manifest.json`、`App.tsx:533-580`、`src/lib/utils/capabilities.ts:388-413`。

### 1.4 配置与草稿

- 草稿 TTL 24 小时，保存步骤、设备名、服务商、GitHub token、WebDAV 口令、类型、排除项；不保存加密口令（`src/lib/onboarding-draft.ts`）。
- 保存成功即清草稿并把 `onboarding_completed` 置真。
- 备份导入复用同一套确认对话（`settings-import.ts`），含 E2EE 关闭、后端变更、明文凭据、Drive 会话四类风险提示——这块做得比向导本身更完整。

## 2. 问题清单

### P0 — 会破坏配置、误导用户或损伤信任

#### P0-1 已配置用户重入会覆盖配置

- **现象**：`onboarding.html` 无 `onboarding_completed` 守卫。挂载逻辑只读 `device_label` 与 `first_sync_pending`（`App.tsx:316-380`）；`finish()` 以向导状态覆写（`App.tsx:612-624`）。
- **具体后果**：
  1. 用户在已完成的标签页按刷新/后退 → 草稿已清 → 回到 `welcome`，`dataTypes` 是默认 `{bookmarks:true, 其余 false}`。
  2. 再点完成 → `backends` 被替换成"只有一个当前选中后端"的数组，其他已配置后端消失；`enabled_types` 被重置为仅书签。
- **触发成本极低**：`TROUBLESHOOTING.md` 的 "Starting over" 教用户重装；重装后旧标签页、书签都可能再次打开该页。
- **建议**：入口三态判定（见 3.1），未传 `reason` 且已配置时进入 `manage` 模式或重定向到设置页；向导内部再加一道保存前确认。

```tsx
// App.tsx 挂载阶段
const settings = res.ok && res.res.type === "SETTINGS" ? res.res.payload : null;
if (settings?.onboarding_completed && !PERMISSION_MODE && !RECONFIGURE) {
  // manage 模式：只读摘要 + "重新配置"显式入口
  setEntry("manage");
  return;
}
```

#### P0-2 首帧总先渲染 `welcome`

- **现象**：`useState<Step>("welcome")`（`App.tsx:85`）+ `restored=false` 期间不拦渲染。更新模式的 `permissions` 靠 effect 才切换（`304-314`）。
- **后果**：更新后打开权限页，用户先看到 200–500ms 的"欢迎使用 Kesonode + 设备名输入框"再跳到权限页；从草稿恢复到 `encrypt` 的用户同样先闪一次第一步。这是最容易被截图吐槽的那类问题。
- **建议**：`useState<Step>(PERMISSION_MODE ? "permissions" : "welcome")`；`restored` 为假时渲染等高骨架，避免布局跳动。

#### P0-3 权限页说技术术语，不说人话

- **现象**：`missingPerms.permissions.map(...)` 直接输出 `history` / `tabs` / `management`，主机权限输出 `https://xxx/*`，等宽字体（`App.tsx:1380-1389`）。
- **后果**：用户看到一个自己没听说过的 API 名，无法判断该不该给；这是"授权页跳出率"的主要来源。
- **建议**：建立 `permission → { 人话名称, 用途, 拒绝后果 }` 映射（3.4），标识符仅放在次要位置或折叠区。

#### P0-4 安装期权限面过大，与用户实际选择无关

- **现象**：`host_permissions` 硬编码 4 个 Google/GitHub 域名。只用 WebDAV 的用户在安装时也要接受"读取和更改您在 googleapis.com / api.github.com 上的数据"。
- **后果**：安装转化率与信任成本直接受损；而 WebDAV 路径本来就走 `optional_host_permissions`，说明这条模式技术上可行。
- **建议**：迁移到 `optional_host_permissions`，在用户点击 GDrive/GitHub 卡片时随手势申请；同步扩展 `missingPermissionsFor()` 覆盖 gdrive/github 主机，否则权限被撤销后会变成静默失败。
- **风险与验证点**：`identity.launchWebAuthFlow` 的授权页本身通常不需要主机权限，但换取 token 的 `fetch` 需要；Firefox 上必须实测一次授权→刷新→同步全链路，再决定是否迁移。

#### P0-5 数据步骤允许"零类型"通过

- **现象**：`data` 步骤"继续"无校验（`App.tsx:1123`），全部关闭也能进入加密与完成；`enabled_types: []` 保存成功后 `SYNC_NOW` 立即失败，走 `syncing` 的错误分支，而 `done` 页仍是"一切就绪"。
- **证据**：弹窗为这个状态专门写了 `nothingEnabled` 分支（`popup/App.tsx:452-470`），说明线上确实会走到。
- **建议**：至少一项为真才可继续，文案说明"关闭全部将无法同步"；或提供显式"暂不同步"通道并让完成页如实呈现。

### P1 — 流程与界面

| 编号 | 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P1-1 | 设备名在两个步骤各问一次 | `806-813`、`1105-1116` | 重复劳动，像是没记住上一步 | 只保留 data 步骤（紧邻同步范围），欢迎页改为展示自动检测名 |
| P1-2 | 存储步骤 8 张卡片平铺、认证面板内联 | `838-998` | 首屏看不到"继续"，选型决策成本高 | 分组（推荐 / 自托管 / 其他）+ 折叠认证面板 + 吸底导航 |
| P1-3 | 进度点无标签、不可回跳、`fixed` 定位 | `771-780`、`1448-1451` | 用户不知道还剩几步；小屏上与卡片内容重叠 | 步骤名 + "第 n / 共 4 步"，已完成步骤可点击回跳 |

| P1-6 | 完成页与"第二台设备"核心循环脱节 | `1344-1368` | 同步产品的价值在第二台设备，此处无任何引导 | 完成页加"在另一台设备选择同一存储"步骤 + 首次同步结果摘要 |
| P1-7 | 权限弹窗无预期管理 | `finish()` 内直接 `permissions.request` | 用户点"完成并同步"后突然弹系统窗，容易直接拒绝 | 按钮上方预先列出"接下来会申请什么、为什么" |
| P1-8 | E2EE 默认关，文案却写"推荐" | `256`（`useState(false)`）+ `onb_e2ee_desc` | 文案与默认值自相矛盾，安全姿态模糊 | 二选一：默认开（强化恢复提示），或去掉"推荐"改为中性说明 |
| P1-9 | 无退出/"稍后继续" | 全页无关闭入口 | 被迫一次做完，移动端易中断 | 角落"稍后继续"，说明草稿保留 24 小时及再次入口 |
| P1-10 | 设置页与弹窗的兜底卡片口径不一 | `options 1556-1584`（2 步）vs 向导 4 步 | 用户在两处看到不同"完成度"定义 | 统一为同一份步骤定义（存储 / 内容 / 安全 / 连接） |

### P2 — 一致性与打磨

- **P2-1 emoji 图标**：`🔒⚡🌐📦🎉✅` 与设置页 lucide 体系混用，Windows/Linux 渲染差异明显，削弱专业感。建议统一为 lucide + 品牌色块。
- **P2-2 无步骤级无障碍语义**：圆点无 `aria`，步骤切换不迁移焦点、不更新 `document.title`。建议 `role="progressbar"` + 切换时聚焦 `h1`。
- **P2-3 无权限健康总览**：设置页有单类型"权限丢失"警告（`options:2010-2030`），但没有一处能看到"必需/可选/已撤销"的全集与一键补授。
- **P2-4 导入后无自检**：导入成功即宣告完成，未验证存储可达、口令可解、权限齐备。
- **P2-5 无"重新运行引导"入口**：`TROUBLESHOOTING` 让用户重装，其实一个受控的 manage 模式更安全。
- **P2-6 语言**：`ar`/`et`/`ja` 目录只有 4/25/50 条，逐条回退英文会造成中英混排（`ja` 尤其明显）；`shipped-languages.json` 未包含这三种，建议在发布脚本里拦住未达标语言，或补齐后再进包。

## 3. 目标方案

### 3.1 入口三态

```
reason=permissions          → update 模式（只做权限与变更说明，绝不写配置）
无 reason 且已配置           → manage 模式（只读摘要 + 重新配置 / 自检 / 导出）
无 reason 且未配置           → setup 模式（现有向导）
```

`manage` 模式是新增的关键页面，承担三件事：展示当前存储/类型/加密/权限状态；提供"重新配置"（进入向导但预填现有值，保存前二次确认）；提供"重新运行自检"。

### 3.2 首次安装：重排为 5 步

| 步骤 | 内容 | 相对现状的改动 |
|---|---|---|
| 1 欢迎 | 一句价值主张 + "3 步完成、无需账号" + **可折叠的权限透明说明**（访问书签做什么、为什么没有服务器） | 移除设备名与导入面板；卖点从 4 条 emoji 改为 3 条带图标的要点 |
| 2 存储 | 分组卡片（推荐/自托管/其他），认证面板折叠，吸底"继续" | 8 张卡片不再纵向平铺；WebDAV 卡片预先说明"稍后会请求访问该服务器" |
| 3 内容 | 4 个类型（每项注明所需权限与用途）+ 至少一项校验 + 设备名（唯一入口）+ 书签排除 | 移除欢迎页的重复字段；补齐零选择校验 |
| 4 安全 | E2EE + 口令/确认/生成 + 恢复提示 | 默认值与文案对齐；加口令强度提示与"我已妥善保存"确认 |
| 5 连接 | 权限预说明 → 申请 → 保存 → 首次同步进度 | 权限弹窗前有清单，不再是突然弹出 |

结果页（不计入步骤）：首次同步摘要（各类型数量/状态）+ 第二台设备引导 + 加密与权限状态回顾 + "完成"。

### 3.3 更新：有动作才打扰

```
update 事件
 ├─ 计算 needsAction = 缺失权限 ∪ 本版新增的必需能力 ∪ 破坏性变更
 ├─ needsAction 非空 → 打开 update 页：本版 3 条变更 + 需要你做 1 件事 + 授权按钮
 └─ 为空 → 不打开页面；弹窗显示一次性 "已更新至 vX.Y.Z · 查看变更"
```

要点：更新页与 setup 向导**共用组件但不共用状态机**，避免 P0-1 那类覆写；变更条目从仓库内的结构化文件读取（可与 `CHANGELOG.md` 同源），不再散落在 i18n 键里。

### 3.4 权限引导：三段式 + 人话映射

每条权限固定三段：**是什么 → Kesonode 用它做什么 → 拒绝会怎样**。

| 标识符 | 人话名称 | 用途 | 拒绝后果 |
|---|---|---|---|
| `bookmarks` | 书签 | 读取与写回，这是同步的核心 | 无法使用 Kesonode |
| `history` | 浏览记录 | 仅同步最近 N 天（设置项），上传前按你的选择加密 | 浏览记录停止同步，其他不受影响 |
| `tabs` | 打开的标签页 | 会话同步与跨设备恢复 | 会话停止同步 |
| `tabGroups` | 标签组名称与颜色 | 让恢复的标签页回到原分组 | 标签页恢复但不分组 |
| `management` | 已安装扩展列表 | 仅名称与版本，用于跨设备"缺装提醒" | 扩展列表停止同步 |
| `https://<host>/*` | 你填写的存储服务器 | 仅限该域名，用于读写同步文件 | 该存储不可用 |

更新页的标题也应从"新版本需要重新授权"改为"同步需要你确认 N 项权限"，避免让用户以为是付费墙或强制授权。

### 3.5 配置引导：自检与恢复

- **自检（setup 完成页 + 设置页各一处）**：存储写入→读取→删除探针；加密往返一次；权限清单比对；返回"4 项通过 / 1 项待处理"及对应修复按钮。
- **多设备**：完成页给出"在另一台设备安装 Kesonode，选择同一个存储即可"，并显示当前存储的人类可读名（如 `Koofr`，不是 `webdav`）。
- **恢复**：导入备份后不要立刻宣告完成，先跑一次自检，把"需要补权限"以清单形式留在页面上。
- **重新配置**：manage 模式提供，预填现值，保存前明确列出"将被覆盖的项"。

### 3.6 manifest 收敛（需实测后执行）

```diff
-  "host_permissions": ["https://www.googleapis.com/*", "https://oauth2.googleapis.com/*",
-                        "https://accounts.google.com/*", "https://api.github.com/*"],
   "optional_host_permissions": ["https://*/*", "http://localhost/*", "http://127.0.0.1/*"]
```

配套改动：`missingPermissionsFor()` 增加 gdrive/github 的主机判定；`connectGDrive` / GitHub 校验前先申请主机权限；更新页能识别"主机权限被撤销"。若实测发现 OAuth 依赖安装期权限，则退化为只把 GitHub 域名改为可选。

## 4. 文案草案（中文）

## 6. 不建议做的两件事

1. **不要在权限页加入"跳过"。** 同步类扩展跳过权限会直接变成静默失败，比拒绝更伤人。应当做的是把"为什么"讲清楚，以及给出去浏览器设置里手动授权的可执行路径（移动端已是唯一路径）。
2. **不要把更新提示做成每次版本都强弹页面。** 补丁版本频繁，强弹会迅速被用户训练成"无脑关闭"，反而让真正的必需授权被忽略。
